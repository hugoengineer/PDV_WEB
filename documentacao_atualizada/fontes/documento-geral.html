Sumário

Apresentação do Projeto

O PDV Web é uma solução de ponto de venda para o varejo, focada em processar vendas com rapidez, controlar estoque e caixa com rigor e impedir perdas financeiras por descontos indevidos, vendas sem saldo ou cancelamentos sem controle. O sistema opera como aplicação web, containerizada em Docker e preparada para hospedagem em nuvem (AWS EC2), com duas visões de uso: Vendedor e Gerente.

O problema

Divergência entre estoque físico e sistema, descontos concedidos sem autorização, comissões calculadas à mão e nenhum registro de quem fez cada operação sensível.

O objetivo

Uma frente de caixa web com controle de acesso por perfil, estoque atualizado em tempo real, caixa com abertura, sangria e fechamento, e comissão automática por vendedor.

A solução

Uma API REST segura (Spring Boot + PostgreSQL), executando em containers Docker, com todas as regras de negócio no servidor e 320 execuções de testes automatizados aprovadas.

Premissas, restrições e riscos

Premissas

  • Autenticação por CPF e senha obrigatória desde o primeiro acesso
  • Conexão contínua com a internet/nuvem para atualização simultânea dos dados
  • Dois atores principais: Vendedor e Gerente

Restrições

  • Cancelamento de vendas concluídas é exclusivo do Gerente
  • Não são permitidas vendas com estoque zerado ou acima do disponível

Riscos e mitigação

  • Segurança: acesso indevido → CPF/senha com hash, JWT, perfis
  • Estoque: vendas simultâneas → bloqueio de linha no banco
  • Financeiro: descontos indevidos → só por cupom ou autorização do Gerente

Autenticação UC01
  • Login por CPF (com ou sem máscara) e senha
  • Token JWT válido por 24 h, com renovação (refresh-token)
  • Logout invalida o token na hora, mesmo após reinício da API
  • Troca de senha com conferência da senha atual (mín. 8 caracteres)
  • Tentativas de login com falha registradas na auditoria; 5 erros bloqueiam por 15 min
POST /auth/login · /refresh-token · /logout · PATCH /auth/alterar-senha
Controle de caixa UC02 · UC03 · UC15

  • Saldo em dinheiro do turno em tempo real
  • Sangria (retirada) e suprimento (reforço) com justificativa, só pelo gerente
  • Sangria nunca maior que o dinheiro no caixa
  • Fechamento: valor contado × esperado, com a diferença (sobra/falta)

Registro de venda UC04 · UC05

Auditoria UC16 · Regra 1.2
Toda ação sensível gera um registro com quem, quando, o quê e os valores anterior e novo: login (sucesso e falha), abertura/fechamento de caixa, sangria, suprimento, venda, desconto do gerente, cancelamento, cadastros e alterações de produtos, preços, estoque, clientes, cupons e funcionários. Se a operação falhar, o registro também é desfeito: nunca há LOG de algo que não aconteceu. No banco, gatilhos tornam o LOG "somente inclusão".

Segurança

Autenticação

  • Senhas guardadas só como hash BCrypt
  • Login com erro devolve sempre a mesma mensagem e leva o mesmo tempo: não revela se o CPF existe
  • Token JWT assinado (HS256); a aplicação não sobe sem uma chave secreta forte
  • Logout e renovação invalidam o token anterior

Autorização

  • Perfis verificados em duas camadas
  • Usuário inativado ou com perfil alterado perde o acesso na hora, sem esperar o token expirar
  • Proteção contra acesso a dados de outro usuário trocando o ID na URL
  • Desconto direto exige perfil de gerente ou a senha de um gerente ativo

Integridade financeira

  • Preço vem sempre do catálogo; preço adulterado na requisição é ignorado
  • Venda inteira numa única transação; qualquer falha desfaz tudo
  • Restrições no banco: estoque ≥ 0, total = subtotal − descontos, documento único
  • Vendas imutáveis; cancelamento só com motivo e auditoria; gatilhos impedem adulteração por SQL direto
  • API conecta com um papel sem permissão de alterar tabelas (pdv_app)

Privacidade e erros

  • Erros nunca expõem SQL, stack trace ou dados de conexão
  • Banco indisponível → 503 genérico
  • CPF mascarado nos registros de tentativas de login (LGPD)
  • 5 senhas erradas bloqueiam o login por 15 min (429); o mesmo vale para a senha do gerente no desconto
  • Logout gravado no banco: vale após reinício e entre servidores
  • HTTPS obrigatório e HSTS ativáveis por configuração
  • Só o health check é público; demais endpoints de monitoramento ficam fechados

As falhas de segurança encontradas pelos testes (DEF-WEB-001 a 005) e suas correções estão na seção 3.3.

Níveis de teste (pirâmide)

Técnicas aplicadas

  • Partição de equivalência: CPF/CNPJ, tipos de pessoa, formas de pagamento, perfis
  • Valores-limite: preço 0,00 × 0,01; estoque = mínimo; desconto = total; sangria = saldo; vigência do cupom ao segundo
  • Tabela de decisão: cupom × desconto direto × perfil × autorização
  • Transição de estados: caixa ABERTO → FECHADO; venda CONCLUIDA → CANCELADA
  • Segurança: token adulterado, outra chave, perfil sem permissão, troca de ID na URL, SQL injection, força bruta
  • Exceção: banco indisponível, JSON malformado, erro inesperado
  • Concorrência: 20 vendas simultâneas do último lote
  • Desempenho e carga: 1.000 produtos; 20 operadores simultâneos
  • Mutação (PIT): mede se os testes detectam erros inseridos no código

Execução fora dos testes automatizados

  • Servidor real: a API subiu como servidor HTTP (modo demonstração) e passou num roteiro de 14 passos com curl: health check, Swagger, login dos dois perfis, venda do exemplo do contrato (R$ 215,00, comissão R$ 10,75), bloqueio por estoque (422), sangria negada ao vendedor (403), fechamento sem diferença, bloqueio de login (429), logout e cabeçalhos de segurança.
