DEF-WEB-001 — Vendedor recebe 400 em vez de 403 em operações exclusivas do Gerente

Campo Valor
Severidade / prioridade Média / P1 (segurança — exposição de informação)
Status Fechado (corrigido, retestado, regressão aprovada)
Módulo seguranca/ConfiguracaoSeguranca
Encontrado por CT-SEG-005 (matriz RBAC) — 5 de 9 operações falharam na primeira execução
Passos para reproduzir 1. Autenticar como Vendedor. 2. POST /produtos com corpo {}.
Resultado esperado 403 acesso-negado, sem processar o corpo
Resultado obtido 400 validacao listando os campos obrigatórios (nome, preco_venda, …)
Causa raiz A autorização ficava só no @PreAuthorize do controller, avaliado depois da leitura e validação (@Valid) do corpo. Um usuário sem permissão conseguia mapear as regras de validação de operações às quais não tem acesso.
Correção Autorização por rota no SecurityFilterChain, aplicada antes do processamento MVC. O @PreAuthorize permanece como segunda camada.
Reteste CT-SEG-005 9/9 · SegurancaIT 16/16 · ProdutoControllerWebTest 12/12 · regressão final 264/264

DEF-WEB-002 — Gerente rebaixado mantinha os privilégios de gerente até o token expirar

Campo Valor
Severidade / prioridade Alta / P1 (segurança — retenção de privilégio por até 24 h)
Status Fechado (corrigido, retestado, regressão aprovada)
Módulo seguranca/ConfiguracaoSeguranca, usuario/UsuarioRepository
Encontrado por Análise de risco ao escrever a sessão exploratória EXP-02 ("o perfil fica no token até expirar?"). A hipótese foi transformada no caso automatizado CT-SEG-009, que falhou na primeira execução.
Passos para reproduzir 1. Promover um vendedor a GERENTE. 2. Ele faz login (token com perfil = GERENTE). 3. Outro gerente o rebaixa a VENDEDOR. 4. Com o token antigo, GET /usuarios.
Resultado esperado 401 (token invalidado pela mudança de perfil)
Resultado obtido 200 — o usuário rebaixado continuava listando funcionários e poderia cancelar vendas, dar descontos e fazer sangrias por até 24 h
Causa raiz O perfil é gravado como claim no JWT e usado para a autorização; o validador conferia só se o usuário estava ativo, não se o perfil ainda era o mesmo.
Correção O validador do JWT passou a exigir usuário ativo e perfil igual ao da emissão (existsByIdAndAtivoTrueAndPerfil). Qualquer mudança de perfil invalida os tokens anteriores; o usuário faz login de novo e recebe o perfil atualizado.
Reteste CT-SEG-009 aprovado · SegurancaIT 17/17 · AutenticacaoIT 9/9 · UsuarioIT 9/9 · regressão final 265/265

DEF-WEB-007 — Restauração de backup falhava no Git Bash e deixava a API parada

Campo Valor
Severidade / prioridade Média / P1 (disponibilidade — recuperação de desastre)
Status Fechado
Módulo scripts/restaurar-backup.sh
Encontrado por RT-DEP-07
Resultado obtido pg_restore: could not open input file "C:/Program Files/Git/backups/…"; o banco ficou intacto (transação única), mas a API continuou parada

DEF-WEB-008 — subir-docker.sh pedia senha e terminava com erro mesmo com o ambiente saudável

Campo Valor
Severidade / prioridade Baixa / P2 (falso alarme na implantação)
Status Fechado

DEF-WEB-009 — Em modo produção (PDV_EXIGIR_HTTPS=true) o health check marcaria a API como "unhealthy"

Campo Valor
Severidade / prioridade Média / P1 (disponibilidade — o proxy depende de a API estar "healthy" para subir)
Status Fechado
Módulo docker-compose.yml (health check do serviço api)
Encontrado por Inspeção, ao preparar o proxy TLS para RT-DEP-05 (antes de qualquer execução em produção)
Resultado esperado sem correção O health check chama /actuator/health por HTTP sem cabeçalho de proxy; com HTTPS obrigatório a API responde 302, a verificação de "UP" falha e o container fica "unhealthy"

DEF-TST-001 — Cenários BDD de desconto liam "10.00" como 1000 (defeito no script de teste)

Campo Valor
Severidade / prioridade Baixa / P2 (não afeta o produto, mas causava falso negativo)
Status Fechado
Encontrado por BDD-DES R5, R6 e R7 — 3 de 18 cenários falharam: esperado 201, obtido 422 desconto-invalido
Análise A API estava correta: recebeu desconto de R$ 1.000,00 e o rejeitou. O tipo {bigdecimal} do Cucumber usa o idioma da feature (# language: pt), em que o ponto é separador de milhar.
Correção O passo recebe o valor como texto ({word}) e converte com new BigDecimal(...) (PassosPdv).
Reteste 18/18 cenários, 130/130 passos
Lição registrada Em features em português, valores decimais devem ser lidos como texto ou com vírgula.

Incidente de ambiente INC-01 (não é defeito)

Na primeira execução do ProdutoControllerWebTest, os 12 casos deram erro (contexto não inicializou: faltava o bean HttpSecurity). No Spring Boot 4, o slice @WebMvcTest só configura a segurança com o módulo spring-boot-starter-security-test. A dependência foi ajustada no pom.xml e os 12 casos passaram. Nenhuma mudança no produto.
